# Crit-Ready

**讓設計師在任何一場 design review 裡，都說得出「為什麼」。**

一包給 AI Agent 使用的 UX 設計專案知識模板。不是文件工具，是決策軌跡系統。

---

## 這是給誰的

B2B 企業軟體的 UX 設計師，特別是年資 0–3 年、還在累積話語權的人。

如果下面這些你認得，這包東西就是寫給你的：

1. **決定沒有落點。** Slack、standup 口頭、會議裡做的決定，沒有一個你能搜尋的地方。
2. **分不出「決定」和「提議」。** 工程師說「我先設 50」——這到底算不算定案？
3. **Rationale 只活在當下。** 你知道為什麼，但沒存起來，下次被問還要重想一遍。
4. **來源打架時不知道誰贏。** Jira 寫 100、會議決議 50，你每次都要去問人。
5. **你不在場的會議，脈絡就斷了。** 而你很常不在場。

這五件事的共同結果是：你在 design review 被問「你為什麼選這版」，只講得出「因為這樣比較清楚」。

## 你可能已經試過的方法

| 試過的 | 為什麼沒用 |
| :--- | :--- |
| 寫更完整的 design doc | 完整到沒人讀完。而且寫的當下脈絡已經流失一半 |
| 會後寄總結信 | 一次性、不可檢索，三天後沉到信箱底 |
| 上簡報／溝通課 | 講得好但記不住，下次同一個問題還要重想 |
| 等資深一點再爭取進會議 | 資深不會讓你進到更多房間，只會讓更多房間同時在開 |
| 用 Granola / ChatGPT 自動摘要 | 捏造發言人、濾掉 edge case。被燙過一次就再也不敢信 |

這些方法有一個共同的斷點：**它們都假設「記錄決策」是人的工作。** 人要寫、人要記、人要在場、人要重述。瓶頸永遠是人類的注意力和記憶。

---

## 核心主張

> **專案文件不是給人讀的，是給 Agent 檢索的知識庫。**

一旦接受這件事，設計就不再受限於人類的閱讀負荷，而是專注在兩個真正的問題上：**資訊歸屬錯誤**，以及**多來源矛盾**。

人只負責提供差異（diff），脈絡讓 Agent 自己找。

---

## Log → Link → Lock

| 階段 | 做什麼 | 解掉哪個痛點 |
| :--- | :--- | :--- |
| **Log** | 忠實記錄，先不判斷。明確區分「確認的決策」與「隨口的提議」 | 1、2 |
| **Link** | 每條決策連回商業目標，附上可回溯的來源。沒有來源就不能定案 | 3 |
| **Lock** | 封閉承諾、標記推翻、產出可貼給 stakeholder 的確認語句 | 4 |

## 三個機制

### 1. `#sync`｜低摩擦決策同步

設計師在會議、Figma 留言或 Slack 裡做的決定，往往因為「重述脈絡太花時間」而沒被記錄，於是決策漂移。

你只需要輸入一句話：

```
#sync CSV 上限改為 50 by Nancy。原因：後端限制
```

Agent 會自動比對舊決策、標記 `Superseded`、關閉相關的 Open Question，並產出一句可以直接貼進 Slack 的 lock-in 確認語句。

### 2. 嚴格歸屬｜Granola Prompting

AI 會議工具常憑空捏造發言人。這些錯誤一旦被寫進知識庫，會產生蝴蝶效應。

`granola-custom-template.md` 強制執行歸屬清理，把「確認的決策」和「隨口的提議」拆成兩個獨立區塊，並要求每條決策連回商業目標。最重要的是：**每一種輸出都路由到指定的本地檔案，不是一個黑盒子。**

缺 rationale 的決策不會安靜地通過——它會被標記 🚩，自動降級成 Open Question。

### 3. 來源仲裁｜衝突時不用問人

```
逐字稿  >  會議紀錄  >  Jira / Linear ticket  >  Figma 留言 / Slack
```

Ticket 是落後指標。它在 sprint 開始前就寫好了，而決策是在之後的每一場會議裡改的。**ticket 跟會議決議打架時，會議贏**，然後把落差 flag 給 PM。

### 4. 動態 PARA 適應

路徑不寫死。Agent 在執行 `/init` 前會先掃描根目錄，自己找出代表 Projects 和 Templates 的資料夾（`10-projects`、`1-Project`、`Projects` 都可以）。這讓整套工作流可以帶去任何命名習慣的 vault。

## 內容物

### `templates/design-project/`

| 檔案 | 作用 |
| :--- | :--- |
| `FOLDER-INSTRUCTIONS.md` | 該專案的 Agent 大腦。身分、File Map、`#sync` 規則、來源優先序、Kickoff 必答題 |
| `granola-custom-template.md` | 會議逐字稿的客製 prompt。歸屬清理 + 路由指令 |
| `meeting-notes.md` | 每場會議一則，最新在上。第二順位真相來源 |
| `design-decisions.md` | 決策軌跡。含 5 種 Status 與升級規則 |
| `open-questions.md` | 待釐清問題，標 urgency 與「卡住什麼」 |
| `feedback-tracker.md` | Stakeholder 回饋，分類為 valid / 誤解 / 個人偏好 |
| `working-notes.md` | 暫存區。Informal log、已知缺口、尚在發散的討論、取捨紀錄 |
| `project-brief.md` | 問題、範圍、限制、完成定義。含版本封存機制 |
| `deliverables.md` | 交付了什麼、給了誰、是否已過時 |
| `changelog.md` | 所有異動的稽核軌跡 |

### `.agents/skills/init-project/`

`/init` 指令的腳本。自動偵測 PARA 架構、建立資料夾、複製模板，並強制反問你三個 Kickoff 問題。

---

## 如何使用

1. 把 `templates/` 與 `.agents/` 的內容複製到你的 Obsidian 或 PARA vault 根目錄
2. 啟動你的 Agent（Claude Code、Antigravity 等）
3. 輸入：

   ```
   /init work-你的專案名稱
   ```

4. Agent 會架好資料夾結構，並反問你「成功長什麼樣」「怎麼衡量」「誰負責衡量」

---

## 這套系統目前解不了什麼

**痛點 5（你不在場的會議）只解了一半。**

Granola template 會標記「有已知反對意見的人缺席」，但那處理的是**別人**缺席。如果缺席的是你自己，這份 prompt 根本不會被執行——你沒參加，就沒有逐字稿可以餵進去。

反向流程（拿著你的 Open Questions 回去查別人的會議紀錄）目前不在這包模板裡。

## 致謝

決策的表述方式參考自 Tom Greever《Articulating Design Decisions》。本模板的貢獻在於：把「當場講清楚」延伸成「事後查得到」。
